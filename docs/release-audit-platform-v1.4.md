# Platform v1.4 发布与部署审计

> 审计日期：2026-07-26
> 发布前线上提交：`693644e1a4ae1bdc6e86f9e46e35eaea399396ee`
> 状态：已发布并完成生产验收

## 1. 发布目标

本候选发布阶段9的用户治理、资料审核和管理中台，不修改普通RAG的Prompt、
Embedding模型、检索算法、`top_k`、Chroma集合、SSE事件或生产实验开关。阶段10的
备份恢复脚本随代码归档，但生产自动备份和整机重启恢复已经在业务发布前独立验收；
本次不同时修改Nginx、域名或HTTPS。

## 2. 发布范围

- `user/admin/super_admin`三层数据库角色、集中权限策略和最后超级管理员保护。
- 个人中心、资料隔离提交、审核批准/拒绝、知识资产版本/下线/重发/替换。
- 任务、审计、安全重试和超级管理员用户治理。
- 审核原子状态抢占、发布失败补偿和发布后隔离文件待清理告警。
- 统一AppShell、分角色菜单/路由，以及个人和管理页面。
- Alembic `0006`至`0010`；既有文档只登记为`published`和版本1，不重新Embedding。
- 自动备份、受控恢复、隔离恢复演练和systemd定时模板。
- 对应自动化测试、产品规范、技术设计、部署手册和handoff。

## 3. 明确排除

- `.env`、密钥、数据库、上传文件、Chroma、Redis数据、日志、备份和医学正文。
- Agent、质量反馈、记忆、复杂文档解析。
- RAG质量调参、混合检索或Reranker启用。
- 域名、HTTPS和Nginx拓扑变更。
- 未经费用预检的真实Embedding、Reranker或Qwen调用。

## 4. 黑盒数据流

```text
普通用户提交PDF/TXT
-> 文件只进入隔离目录并做无费用解析预览
-> 管理员以原子状态迁移批准或拒绝
-> 批准后才进入共享文档生命周期和Embedding/Chroma
-> 成功写published文档、版本、完成任务和审计
-> 隔离文件清理失败只留下cleanup_pending告警
-> 普通RAG继续只检索生产Chroma中的published资料
```

角色真相源是MySQL。前端菜单和路由只改善体验，所有管理接口仍由后端数据库角色授权。

## 6. 数据迁移与回退

- 更新前重新执行生产备份，并记录目录、清单校验和、旧提交和旧镜像标签。
- 后端新镜像启动时先自动执行`alembic upgrade head`；迁移失败则容器不能进入健康状态，
  立即停止，不继续前端或业务验收。
- 迁移只新增治理表、角色约束和版本登记；既有27份文档不得调用Embedding或改写Chroma。
- 未对外开放新提交前如需代码回退，回退旧镜像并将数据库降级到`0005_user_role`。
- 一旦产生阶段9新业务数据，不直接降级丢表；使用已验证的生产备份整体恢复，并保留故障
  现场备份供审计。
- 禁止`docker compose down -v`，禁止在服务器直接编辑业务源码。

## 7. 部署顺序

1. 精确提交并推送本审计范围，记录候选SHA。
2. 使用生产相对地址构建前端，确认产物包含`/api/v1`且不包含`127.0.0.1:8000`。
3. 生产重新执行校验备份，保留当前backend/web镜像回滚标签。
4. 服务器工作树必须干净并快进到候选SHA，上传对应前端产物。
5. 只重建backend和web；MySQL、Redis和四个命名卷不删除、不重建。
6. 先验证迁移head、四容器健康、原数据计数和公开接口，再做三层角色与管理页面免费验收。
7. 付费RAG验收必须另做费用预检、限制调用次数，并在完成后清理临时账号、会话和资料。
