# 项目愿景与产品边界

## 1. 为什么做这个项目

项目作者的求职方向是 Python 后端开发和大模型应用开发。原始课程项目使用 Streamlit，适合学习 RAG 和 Agent，但无法充分展示前后端分离、数据库设计、接口治理、测试和部署能力。

本项目不是简单更换页面，而是把课程 Demo 持续改造成一个**可运行、可解释、可测试、可扩展的医疗知识库应用**。

## 2. 产品定位

Medical RAG Assistant 面向医学资料学习、科研资料整理和内部知识检索场景。

用户可以：

- 注册并登录自己的账号。
- 对公共知识库提问并查看引用来源。
- 查看只属于自己的历史会话并继续追问。
- 提交 PDF/TXT 医疗资料，在“我的资料”查看审核和处理进度。
- 使用独立Agent完成检索、摘要、对比和学习报告。
- 后续在Codex式Agent会话中连续追问，并查看计划、工具、来源和报告产物。

管理员负责审核用户提交、维护公共知识、处理失败任务和查看质量数据；超级管理员额外负责账号和管理员角色。只有审核发布的资料才进入公共检索。

系统不用于临床诊断，不推荐处方或具体药物剂量，不替代医生判断。

## 3. 当前产品状态

当前阶段1～12已完成：

- Vue 3 与 FastAPI 前后端分离。
- PDF/TXT 上传、解析、切分、SHA-256 去重和删除。
- DashScope Embedding + Chroma 向量检索。
- 通义千问回答、来源引用和知识不足拒答。
- SSE 逐块输出、停止生成和安全错误事件。
- MySQL 会话、消息、来源持久化和多轮上下文。
- 会话新建、切换、刷新恢复和删除。
- Redis限流、并发保护、生成锁和幂等。
- 版本化RAG评估、结构化Telemetry和管理员运行统计。
- Docker Compose云端运行基线。
- 后端、前端组件、SSE 字节分片和构建验证。
- 三层角色、资料审核、个人/管理后台和知识资产治理。
- 受步骤、超时、Token和费用约束的LangGraph Agent。
- 回答质量反馈、滚动摘要、用户显式记忆和复杂PDF解析告警。
- 公网IP受信任HTTPS、自动备份、受控恢复和整机重启恢复。

本地知识库当前登记 27 份较完整的医疗主题文档，共 103 个片段。运行数据不提交 Git。

当前阶段1～12已经完成并发布。现有Agent采用“一项任务对应一次运行”的工作台交互；
Codex式多轮Agent会话、消息历史和连续产物引用属于阶段13目标，不能写成已实现功能。

## 4. 目标用户故事

### 账号与会话

作为注册用户，我登录后只看到自己的历史会话，无法访问其他账号的会话。

### 公共知识库

作为注册用户，我可以检索所有已发布公共医疗资料。我的新提交先进入审核流程，不会立刻污染所有用户的检索结果。

### 我的资料

作为提交者，我可以看到自己资料的解析、审核、发布或失败状态，查看拒绝原因，并在审核前撤回。

### 系统文档管理

作为管理员，我可以审核资料，新增、下线和整份替换系统文档，并查看相关处理任务。作为超级管理员，我可以启停账号和授予或撤销管理员；普通用户和管理员都不能自行提升权限。

### 可靠问答

作为资料使用者，我看到的回答应尽量基于知识库，并能展开查看使用了哪些文件和原文片段。资料不足时系统应明确拒答。

### Agent

作为学习者，我可以在独立Agent工作台连续提出资料任务，让系统在受控循环中选择知识
检索、文档摘要、多文档比较或学习报告工具。我能看到公开计划、工具状态、来源和产物，
也能停止运行并基于上一轮结果继续提问。RAG和Agent只共享已经发布的公共知识。

## 5. 企业化方向

“企业级”在本项目中不等于堆技术或拆微服务，而是逐步具备：

- 清晰的模块职责和依赖方向。
- 身份认证、数据归属和权限校验。
- 数据迁移、失败回滚和一致性检查。
- 限流、重复请求保护和成本控制。
- 可量化的检索评估与回归测试。
- 结构化日志、请求追踪和运行指标。
- 三层角色、资料审核、知识版本、任务和审计。
- 普通用户、管理员和超级管理员各自清晰的工作台。
- 一致、响应式且具备完整加载/空/失败/无权限状态的企业级前端。
- 可控、可审计、有工具上限的 Agent。
- 可重复的 Docker 部署和数据持久化。

### 5.1 对标公开成熟项目的方式

项目会参考 Dify、Langflow、RAGFlow、Coze Studio、OpenHands 等公开项目的工程思路，但不追求复制它们的平台规模：

- 学习 RAGFlow 对文档处理、检索质量和评估的重视。
- 学习 Dify、Langflow、Coze 对工具注册、工作流状态、运行记录和可观测性的拆分。
- 学习 LangGraph Agent Chat、Open WebUI 和 Codex 的会话线程、流式过程、工具状态与产物交互。
- 学习 OpenHands 对执行边界、步骤上限、权限和失败恢复的约束。
- 保留当前项目的医疗资料场景、简单部署和可解释数据流。

对标目标不是“功能数量相同”，而是让每个已实现功能都具备清晰边界、可测试性、故障策略和运行证据。

## 6. 明确不做

- 不训练或在本地服务器运行大模型。
- 不提供医疗诊断、处方或治疗决策。
- 不为了简历拆分微服务、引入消息队列或 Kubernetes。
- 第一版 Agent 不做多 Agent 协作、任意代码执行或通用低代码工作流平台。
- 不在没有评估集的情况下宣称检索效果提升。
- 不让 Agent 访问任意系统命令、数据库或未审核工具。
- 不把尚未实现的功能写成已完成功能。

## 7. 成功标准

项目最终应做到：

1. 新开发者只阅读仓库文档即可继续开发。
2. 每个业务模块可以独立测试，修改一个模块不会无故破坏其他模块。
3. 关键流程有自动化测试和真实页面验收。
4. 能从日志和评估结果解释系统为什么回答正确或失败。
5. 能部署到云服务器，由面试官通过网页完成注册、资料提交、审核发布、提问和查看引用。
6. 项目作者能够用黑盒数据流解释每个核心功能。
