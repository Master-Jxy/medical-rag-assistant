# 产品功能与企业级界面设计

> 最后更新：2026-07-29
> 状态说明：本文定义后续产品页面、角色视图和前端质量标准；未标注为当前实现的内容均属于目标，不得提前写成已完成功能。

本文解决两个问题：

1. 后续新增个人中心、审核后台、Agent和数据看板时，页面放在哪里、谁能看到、数据从哪里来。
2. 前端如何逐步变得清晰、成熟、像可交付的企业应用，而不是把功能堆在几个大页面中。

企业感主要来自稳定的信息架构、明确的权限、完整的页面状态和一致的操作反馈。不要用大面积渐变、巨型宣传标题、装饰卡片或复杂动画代替真实产品能力。

## 1. 产品结构

### 1.1 两条AI业务链路

```text
知识库问答
-> 用户快速提问
-> 一次检索 + 一次回答
-> 返回引用来源

Agent
-> 用户提出摘要、比较或报告任务
-> LangGraph选择一个或多个受控工具
-> 展示步骤、来源和最终产物
```

两条链路使用独立页面、接口、状态和历史记录，但共享同一套状态为`published`的公共知识库。RAG页面不显示Agent工具过程；Agent故障不影响普通问答。

### 1.2 资料治理链路

```text
普通用户提交
-> 我的资料显示处理进度
-> 管理员查看解析预览
-> 批准或拒绝
-> 批准后切片、向量化并发布
-> RAG与Agent可检索
-> 管理员后续替换、下线或归档
```

普通用户上传资料并不等于立即修改全体用户的知识库。这样既保留参与感，也避免无关、错误或恶意资料污染公共检索。

## 2. 角色与可见范围

| 功能 | 普通用户 | 管理员 | 超级管理员 |
| --- | --- | --- | --- |
| 公共知识问答 | 是 | 是 | 是 |
| Agent | 是 | 是 | 是 |
| 查看自己的会话和Agent运行 | 是 | 是 | 是 |
| 提交资料、查看自己的状态 | 是 | 是 | 是 |
| 撤回自己的待审核资料 | 是 | 是 | 是 |
| 审核资料 | 否 | 是 | 是 |
| 管理已发布知识和版本 | 否 | 是 | 是 |
| 查看任务、质量和运行统计 | 否 | 是 | 是 |
| 查看管理审计 | 否 | 是，按范围 | 是 |
| 授予或撤销管理员 | 否 | 否 | 是 |
| 启用或停用账号 | 否 | 否 | 是 |
| 修改系统级设置 | 否 | 否 | 是 |

前端根据角色生成菜单和页面入口，但这只是体验层。后端每个接口仍必须验证角色、对象归属和账号状态。

## 3. 页面地图

### 3.0 未登录区域

| 页面 | 路径 | 核心内容 |
| --- | --- | --- |
| 登录 | `/login` | 邮箱、密码、登录和忘记密码入口 |
| 注册 | `/register` | 邮箱验证码、密码、确认密码和昵称 |
| 重置密码 | `/forgot-password` | 邮箱、验证码、新密码和确认密码 |

阶段16本地代码已经实现上述三页；生产在阶段16发布前仍是原直接注册形态。验证码倒计时
只改善交互，发送频率、验证码过期和错误次数始终由后端决定。忘记密码请求显示统一提示，
不在页面泄露邮箱是否已经注册。

| 导航 | 页面 | 核心内容 |
| --- | --- | --- |
| 用户与角色 | `/super-admin/users` | 搜索、分页、账号启停和管理员授予/撤销 |

| 系统审计 | `/super-admin/audit` | 角色与系统设置相关的完整安全审计 |

第一版不做复杂组织架构、租户、部门、审批流编辑器或自定义角色。先把三层角色做稳定。

## 4. 页面黑盒要求

### 4.1 普通用户工作台

进入页面后：

```text
Vue加载当前用户
-> 并行请求个人统计、最近会话、我的资料
-> 每个区域独立显示加载状态
-> 某个接口失败时只降级对应区域
-> 点击条目进入原业务页面
```

工作台不直接读取MySQL，也不在前端自行统计全部数据。后端提供安全的个人读模型，只返回当前用户可见数据。

### 4.2 我的资料

必须清楚显示：

- 文件名、提交时间、状态、处理进度和允许操作。
- 被拒绝时显示安全、可理解的原因。
- 失败时显示稳定错误类别和是否可以重试，不展示Traceback。
- 审核前可撤回；已发布资料不能由普通用户直接删除全局知识。
- 上传成功只表示“提交成功”，不能误提示“已经入库”。

### 4.3 审核中心

审核详情使用右侧抽屉或独立详情页，展示：

- 原文件信息和内容哈希。
- 解析文本预览、页码、片段预览和格式告警。
- 提交者、来源、标签建议和重复资料提示。
- 批准、拒绝和拒绝原因。
- 审核动作的影响说明：批准后才会产生Embedding费用并进入公共检索。

管理员点击批准后应看到任务状态，不要让浏览器长时间卡住并假装同步完成。

### 4.4 知识资产和任务中心

知识资产列表以表格为主，支持状态、科室、标签、来源、更新时间和版本筛选。替换、下线、重建等高影响动作需要确认，并在完成后展示结果和`request_id`。

任务中心区分`queued/running/completed/failed/cancelled`等技术状态与资料业务状态。任务失败不等于资料已发布；页面不能把两者混为一个字段。

### 4.5 Agent工作台

Agent页按Agent Chat v3.2升级为聊天优先的任务工作台。聊天是用户交互外壳，受控
LangGraph运行仍是执行内核；它不是普通RAG业务逻辑的复制，也不展示隐藏推理过程。
完整设计见
[`docs/conversational-agent-design.md`](conversational-agent-design.md)。

桌面布局：

- 左侧：新建会话、搜索、历史会话、置顶/归档和运行状态。
- 中间：用户与Agent消息、流式最终结果和固定底部输入区。
- 公开计划、工具步骤、来源和产物作为对应Agent消息的可折叠组成部分，不再占用永久
  第三栏。
- 点击具体来源后临时打开原文抽屉；只有用户主动预览大型产物时才打开临时产物面板。

每条用户消息最多触发一次受控Agent运行。身份、问候、反馈等消息可以0工具直接回答；
缺少对象时先澄清；复杂任务再按需调用1～安全上限个工具。运行过程显示“正在理解任务”
“检索了4份资料”“正在比较2份文档”等用户可理解事件。运行时过程默认展开，完成后
折叠到最终回答上方；不显示Chain-of-Thought、
scratchpad、系统Prompt或模型隐藏推理。用户可以停止、重试、刷新恢复，并基于上一轮
来源或产物继续提问。

RAG和Agent聊天输入框遵守同一焦点规则：首次进入页面、新建会话、切换历史会话，以及
本轮回答或重试真正结束后，输入框在可用状态自动获得焦点；生成期间的禁用状态不能被
绕过。自动聚焦只改善键盘连续操作，不抢占用户正在查看来源、产物或确认对话框时的
交互。

RAG和Agent的助手回答使用同一套安全Markdown视觉语言，允许标题、粗体、列表、引用、
代码和表格表达重点。用户消息始终按纯文本显示，不解释Markdown；解析器禁用原始HTML，
危险协议链接不得变成可点击链接，外部链接必须使用新窗口安全属性。长代码和表格只能在
消息内容区局部滚动，不能造成整页横向溢出。

界面必须同时表达两类历史：

- **会话历史**：连续的用户/Agent消息。
- **运行历史**：某条用户消息关联的计划、工具步骤、费用、状态和产物；它属于该助手
  消息，不是第二套独立任务列表。

移动端只把会话列表放入导航抽屉，中间保留消息、执行状态与输入区；来源和产物在消息内
展开，工具步骤默认折叠，失败步骤自动展开。

Agent页面不得再出现：

- “旧版独立任务”入口或只显示一个旧run的特殊页面分支。
- 永久空白的“来源与产物”栏。
- 以`completed`等英文内部状态作为完成消息的主要标签。
- 只显示UUID前8位的“来源 xxxx”按钮。
- 因REST历史、乐观消息和SSE临时消息简单拼接而产生的重复或倒序气泡。

### 4.6 邮箱账号生命周期与计量界面 `[阶段16本地已完成，生产待发布]`

注册：

```text
输入邮箱
-> 点击发送验证码
-> 按钮进入固定宽度倒计时
-> 输入验证码、密码、确认密码和昵称
-> 注册成功后进入登录页或按冻结接口继续
```

忘记密码：

```text
从登录页进入重置页
-> 输入邮箱并请求验证码
-> 页面统一提示“如果该邮箱已注册，验证码将发送到邮箱”
-> 输入验证码和新密码
-> 重置成功后清除本地登录状态并回到登录页
```

SMTP或Redis故障时，表单保留用户非敏感输入并显示稳定错误和`request_id`；页面不得
展示QQ SMTP授权码、内部Redis键、第三方原始错误或邮箱是否存在。桌面和移动端的验证码
按钮都必须保持固定尺寸，长错误信息不能挤压输入框。

运行统计在阶段16增加以下语义：

- 分开展示输入Token和输出Token。
- 费用必须标注“估算”，并展示已知/未知调用数与计量覆盖率。
- 厂商未返回usage时显示“模型未返回计量”。
- Token已知但单价缺失时显示“单价未配置”，不能显示¥0。
- 确定性回答显示“未调用模型，0 Token，¥0”，不与计量失败混为一类。

## 5. 企业级界面框架

### 5.1 AppShell

桌面端使用稳定应用框架：

```text
左侧导航 224-240px
-> 品牌与系统名
-> 主导航
-> 管理导航（按角色显示）

顶部栏 56-64px
-> 面包屑 / 页面标题
-> 系统状态
-> 通知入口（实现后才显示）
-> 用户菜单

主内容区
-> 页面工具栏
-> 筛选 / 表格 / 工作区域
```

移动端把侧栏改为抽屉，顶栏保留页面标题和菜单按钮。固定宽度的表格在小屏使用横向滚动或转为详情列表，不能压缩到文字重叠。

### 5.2 视觉基线

建议设计变量：

```css
--color-brand-600: #147d6f;
--color-action-600: #2563eb;
--color-bg: #f5f7f8;
--color-surface: #ffffff;
--color-text: #17202a;
--color-text-muted: #66727d;
--color-border: #d8e1e5;
--color-warning: #b7791f;
--color-danger: #c23b3b;
```

规则：

- 品牌绿用于品牌和少量激活状态，操作蓝用于主要命令，警告黄和危险红用于明确风险。
- 页面不能只用深浅不同的绿色；中性色承担大部分背景和文字。
- 卡片圆角不超过8px，阴影轻微；页面区块不做漂浮卡片，卡片里不再嵌套卡片。
- 紧凑面板使用中小字号标题，只有真正的产品首页才使用较大标题。
- 字号不随视口宽度缩放，字间距为0。
- Element Plus按钮使用已有图标；纯图标操作提供`tooltip`和无障碍名称。
- 破坏性操作使用危险样式和二次确认，不能与主要按钮颜色相同。

### 5.3 数据展示

- 列表优先使用表格、筛选栏、分页和批量操作，不把每条记录做成大卡片。
- 数字卡片只显示真正有决策价值的指标，尺寸固定，避免数据加载后跳动。
- 图表必须回答具体问题，例如“审核积压是否增加”，不能为了好看放无意义环图。
- 状态名称、颜色和操作在所有页面保持一致。
- 长文件名、邮箱、错误摘要和文档标题必须截断并提供完整查看方式，不能撑破容器。

## 6. 状态与反馈规范

每个远程数据区域都必须具备：

1. 首次加载：骨架屏或明确加载状态。
2. 空数据：说明当前为空，并给出允许的下一操作。
3. 失败：稳定错误提示、`request_id`和可重试入口。
4. 无权限：403专用提示，不伪装成空列表。
5. 服务降级：例如Redis或Telemetry异常时显示局部状态，不把整站显示为宕机。
6. 成功：保存、提交、审核、撤回和重试均有结果反馈。
7. 长任务：显示任务状态，页面刷新后可以重新查询，不只依赖当前按钮动画。

按钮在请求期间禁用并保持固定尺寸；禁止因为“处理中”文字变长造成布局移动。

## 7. 前端代码边界

目标调用方向：

```text
View
-> Feature组件 / Composable
-> API模块
-> FastAPI
```

- `views`只负责页面组合和页面级加载，不直接堆全部表单、表格、权限和API逻辑。
- `api`集中管理地址、Token、错误映射和SSE解析。
- 角色菜单由统一权限映射生成；页面里可以控制显示，但后端仍是授权真相源。
- 资料状态转换集中在Feature层，不在多个页面重复翻译。
- 可复用筛选、状态徽标、错误面板、确认弹窗和分页表格形成共享组件。
- 暂不为了简历引入复杂状态管理。跨页面账号、角色、菜单和持久筛选明显增长后再引入Pinia；服务器数据仍由API获取，不复制成长期前端真相源。

前端重构采用逐页迁移：

```text
先建立Design Tokens与AppShell
-> 提取通用状态组件
-> 迁移现有概览/问答/知识库
-> 新增个人中心与我的资料
-> 新增管理员页面
-> 最后新增Agent工作台
```

禁止一次性重写所有现有页面。每迁移一个页面，都要保持原接口和已有功能可用。

## 8. 前端验收标准

每个页面任务至少检查：

- 1440和1280宽桌面视口。
- 390宽移动端视口。
- 无文字遮挡、容器溢出、按钮跳动和不必要的整页横向滚动。
- 加载、空、失败、403、成功和长文本状态。
- 键盘焦点可见，表单字段有标签，图标按钮有说明。
- API错误不会只写入控制台而页面无反馈。
- 浏览器控制台无未处理异常。
- 不在页面展示实现说明、快捷键教程或“本页用了什么技术”等开发文字。

涉及固定尺寸面板、表格、流式聊天或图表时，使用真实浏览器截图验证桌面和移动端。前端美化只有在不破坏接口、权限、SSE和数据状态的前提下才算完成。

## 9. 暂不实现

- 自定义主题市场和大规模动画系统。
- 类似Dify的拖拽工作流编辑器。
- 多租户组织、部门、复杂RBAC策略编辑器。
- 用户自由安装第三方插件。
- 在2核2G演示服务器上运行本地大模型或重型OCR流水线。

这些能力会显著增加复杂度。当前优先完成角色治理、资料审核、管理中台、受控Agent和可重复部署，让项目具有清晰且可讲述的企业交付链路。
