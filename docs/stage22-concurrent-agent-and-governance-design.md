# Stage 22 多会话并发、助手编排与知识治理设计

> 状态：22.1～22.6 已本地实现，22.7 L3 验收中；尚未提交或生产部署  
> 对标证据：[`stage22-benchmark-and-design-research.md`](stage22-benchmark-and-design-research.md)

## 1. 目标与非目标

### 目标

1. RAG 和 Agent 在某个会话生成时，用户可以新建或切换到另一个会话继续提问。
2. 同一会话仍只能有一个运行；不同会话最多按配置允许有限并发。
3. 侧栏显示运行中 spinner；后台完成且用户未查看时显示未读点。
4. Agent 支持通用助手、患者助手、医生助手、知识库助手四种模式。
5. 复杂任务可执行一次受控协作 handoff，并展示安全的公开计划/工具事件。
6. 消除重复澄清环和不必要的多轮模型调用，建立可验证的 Token 预算。
7. 管理员可以统一替换、下线和永久删除系统资料与用户审核发布资料。

### 非目标

- 不显示隐藏 Chain-of-Thought。
- 不做自由群聊式多 Agent、并行 Agent、工作流画布、插件市场或任意代码执行。
- 不引入 Celery、Kafka、RabbitMQ、Prefect、Temporal 或微服务。
- 不改变公共知识库只包含审核后资料的原则。
- 不在本阶段启用真实模型验收、生产迁移或部署。

## 2. 核心数据流

```text
用户在会话 A 提问
-> 前端为 A 创建独立 StreamHandle
-> 后端按 user_id + surface + conversation_id 获取锁
-> MySQL 创建 pending/streaming 消息或 AgentRun
-> SSE 只更新 A 的缓存和侧栏状态
-> 用户切换到会话 B 并继续提问
-> B 使用另一条锁和另一份 StreamHandle
-> A 后台完成：若当前不在 A，服务端 read marker 不前移，侧栏显示未读点
-> 用户打开 A：加载服务器真相并标记已读
```

## 3. 运行状态与未读契约

### 3.1 数据库真相

`conversations` 与 `agent_threads` 增加：

- `last_read_sequence`：用户确认看过的最后消息序号，默认 0。
- Agent thread 增加 `assistant_mode`，值为
  `general/patient/clinician/knowledge`，默认 `general`。

列表响应统一增加：

- `run_status`: `idle/pending/running/stopping`。
- `active_run_id`: Agent 返回 run ID；RAG 可为空。
- `has_unread`: 存在序号大于 read marker 的终态助手消息。
- `last_message_status`。

未读不保存可漂移的布尔值，而由消息序号和 read marker 推导。打开会话成功加载消息后，
调用专用 `POST .../read` 接口原子前移 marker；只能前移，不能回退。

### 3.2 前端运行注册表

RAG 与 Agent 各自拥有模块级共享 registry：

```text
Map<conversationId, {
  phase, requestId, runId, controller,
  draftMessage, events, error, startedAt
}>
```

每个 SSE handler 在创建时闭包绑定会话 ID，禁止读取“当前选中会话”决定写到哪里。
切换会话或切换业务页面不 abort 旧流；只有用户明确停止对应会话、退出账号、认证失效
或浏览器真正卸载时才停止。重新进入 RAG/Agent 页面时，页面先复用 registry 中的活动
草稿和 timeline，再在流结束后用服务端终态收敛，不能把新鲜 pending 误显示成进程中断。
当前会话只禁用自己的输入器，侧栏的新建、切换和其他安全操作保持可用。

### 3.3 并发保护

- 保留当前同会话 Redis 生成锁。
- 新增用户级 active-run slot，默认 RAG+Agent 合计最多 2 个；配置范围 1～4。
- 获取顺序固定为“用户 slot -> 会话锁”，释放逆序执行，异常和断流必须 `finally` 释放。
- 频率限制与并发槽位是两个概念，不能互相替代。
- 配置启动校验要求 generation lock TTL 大于 Agent 最大运行时间和断流收尾余量。

## 4. 四种助手模式

| 模式 | 主要能力 | 工具范围 | 医疗边界 |
|---|---|---|---|
| 通用助手 | 日常问答、写作、归纳、任务拆解 | 默认无知识工具，必要时可 handoff | 涉及医学时转患者或医生资料助手 |
| 患者助手 | 健康科普、就医准备、检查结果术语解释、风险提示 | 公共知识检索、资料摘要 | 不诊断、不处方；紧急症状优先建议及时就医 |
| 医生助手 | 文献/指南检索、证据对比、病例资料结构化、随访模板 | 公共知识检索、比较、报告 | 输出为资料辅助，保留来源、局限和人工复核提示 |
| 知识库助手 | 文档检索、摘要、比较、学习报告 | 当前全部只读知识工具 | 不越权写库，不处理系统命令 |

模式保存在会话上，创建后可切换；切换只影响后续消息，不改写历史。长期记忆继续通过统一
`MemoryContextProvider` 注入，并按模式使用更小的相关 Top-K 与字符预算。

## 5. 受控多 Agent 协作

### 5.1 角色

- `supervisor`：只负责确定当前模式、任务类别、主 specialist、是否需要一个协作者、工具预算。
- `general_specialist`、`patient_specialist`、`clinician_specialist`、
  `knowledge_specialist`：各自拥有独立 Prompt、允许工具和输出 Schema。
- `safety_reviewer` 不是自由 Agent，只是对医疗输出执行固定规则和必要时的一次结构化模型审查。

### 5.2 约束

- 默认单 specialist；只有跨域任务才允许一次 handoff。
- 每次运行最多 2 个 specialist、1 次 handoff、3 次工具调用、4 次模型调用。
- specialist 之间只传递裁剪后的结构化 `SpecialistBrief`，不传递隐藏推理或完整历史。
- handoff 目标必须存在于注册表，并同时满足模式、角色、工具权限和预算。
- supervisor 不能直接访问数据库、Chroma、Redis 或模型 SDK；工具继续调用公开应用服务。

### 5.3 公开过程

运行中可以显示：

```text
正在判断任务类型
已选择患者助手
准备检索公共知识库
正在调用：知识检索
已获得 4 条可引用资料
正在组织最终回答
```

这些文案由 `public_code + status + tool_label` 模板化生成。模型生成的 plan 先经过长度、
敏感关键词和字段白名单净化；净化失败时退回固定模板。禁止把“请逐步思考”“内部判断”
等内容作为公开过程。

## 6. Token 与重复澄清修复

### 6.1 当前根因

- 一次运行可能分别调用规划、选工具、结果检查和最终回答模型。
- 结果检查会再次携带较大的原始工具结果。
- Agent 上下文最高约 4000 Token，还会叠加最近消息、摘要、记忆和引用。
- 确定性摘要/报告判断只扫描当前消息里的 UUID，没有使用已经传入的 source IDs、引用消息
  或文档名称，因此“总结这个”会重复要求用户提供资料。

### 6.2 修复

1. 建立 `ResolvedReferences`：在规划前统一解析显式 source IDs、引用消息、artifact 和文档名。
2. 确定性路由使用解析后的引用对象，不再只扫描当前文本 UUID。
3. 工具结果进入后续模型前通过 `ToolResultDigest` 裁剪：只保留工具名、状态、来源 ID、
   关键摘要和受控字符数，不重复传五个完整片段。
4. 可确定的工具成功/失败由代码判断，删除不必要的模型 `inspect_result` 调用；只有结果
   模糊时才允许一次结构化审查。
5. 普通直接回答不检索知识库；医学问题是否检索由模式、用户意图和证据需求共同决定。
6. 上下文按“当前任务 > 显式引用 > 相关记忆 > 最近消息 > 旧摘要”分配预算，默认总输入
   预算收紧并记录每部分估算 Token。
7. 保存最近一次 clarification 的规范化键；同一缺口连续出现时不得原样重复，必须使用已有
   引用继续、换一种明确问法或安全结束。
8. usage 继续累计真实供应商返回值，同时额外记录每个 operation 的调用次数和输入 Token，
   用于验证优化而不是用字符数伪造实际计量。

### 6.3 验收基线

- “总结这个”并附 source ID：0 次重复澄清。
- “幼儿什么时候最容易感冒”之后追问“什么时候”：不能凭空把新问题持续改写为“幼儿”。
- 一次知识检索回答不重复向检查模型发送完整检索结果。
- Fake 场景证明调用次数不超过预算；真实模型成本验收需单独授权。

## 7. 知识资产治理

### 7.1 权限真相

- 普通用户只能撤回尚未发布的提交。
- 一旦管理员发布到公共知识库，原提交者不能通过 `/documents/{id}` 永久删除。
- 管理员和超级管理员可以下线、替换和永久删除任意知识资产；所有操作写审计。

### 7.2 替换

- 统一生命周期服务，不再以 `is_system` 作为能否替换的条件。
- 替换时继承资产来源类型、uploader、标签、分类、科室和治理日期。
- 新文件先完成校验、解析、切片和向量化；数据库切换成功后才删除旧向量和旧文件。
- 用户提交资产替换后，submission 更新新的 document ID、文件元数据和 published 状态。
- 对旧资产加行锁；两个管理员同时替换时只有一个成功，另一个返回 409。

### 7.3 永久删除

- 管理员操作必须二次确认，后端仍独立鉴权。
- 删除前锁定文档并核对文件、向量和 submission 关系。
- 先把 submission 标记为 `archived` 并解除 document 关系，再执行可补偿删除。
- 审计保存操作人、资产 ID、来源类型、原因和请求 ID，不保存文档正文。
- 删除失败恢复文件、向量和数据库关系；不得留下 `published + document_id=NULL`。

## 8. API 与 SSE 兼容

- 保留现有 RAG 与 Agent 正文 SSE 事件；新增字段和事件采用向后兼容方式。
- 新增 read endpoint、assistant mode 字段、sidebar run summary。
- Agent 公开事件引入稳定 `event_id/sequence/public_code/public_summary`；旧 `decision`
  在一个版本周期内继续返回兼容映射。
- 删除/替换 API 统一到 `/admin/knowledge-assets/{id}` 下；旧系统资料接口保留兼容代理，
  前端不再按 `is_system` 隐藏操作。

1. **22.1**：本文档、当前代码审计和失败契约测试。
2. **22.2**：先修复已发布资料的用户删除漏洞，再完成管理员统一替换/永久删除。
3. **22.3**：数据库 read marker、Agent mode、列表运行摘要、用户并发槽位和恢复接口。
4. **22.4**：RAG 与 Agent 的按会话 stream registry、spinner、未读点、切换和停止。
5. **22.5**：四种助手模式、受控 supervisor/handoff 和公开事件净化。
6. **22.6**：引用解析、ToolResultDigest、调用次数压缩和重复澄清防护。

8. **22.8**：提交、推送和发布准备；生产部署、迁移和真实模型费用验收单独授权。

## 10. 验收矩阵

- A 会话生成时可创建并使用 B；A/B 消息、Token、步骤和停止控制不串线。
- 同一会话双击仍只产生一个运行；第三个并发会话按配置返回明确繁忙提示。
- 后台完成显示未读点，打开后消失；刷新后状态不丢失。
- 删除、归档当前会话不会把仍在运行的其他会话状态写错。
- 四种模式权限、工具和医学边界由后端强制，不能靠前端下拉框绕过。
- handoff 不超过一次，工具和模型调用不超过预算，刷新后公开过程可恢复。
- metadata、SSE、日志和数据库中不存在隐藏推理字段。
- 已发布用户资料不能由原用户删除；管理员替换/删除有行锁、补偿、审计和 submission 一致性。
- `backend/app/modules/auth/service.py` 的既有用户修改保持不变。
